# rspack-coverage

`rspack-coverage` connects a final Rspack compilation with a manually exported Chrome DevTools JavaScript Coverage recording. It shows which chunks loaded, which generated bytes executed, how those bytes map back to original files and lines, and which compilation reference edges retain a module.

It is an independent local tool. Its small local CLI only reopens captured build data; there is no browser extension, instrumentation, remote upload, telemetry, or Rsdoctor requirement.

## Install

```bash
pnpm add -D rspack-coverage
```

```ts
// rspack.config.ts
import { RspackCoveragePlugin } from "rspack-coverage";

export default {
  plugins: [new RspackCoveragePlugin()],
};
```

Run the project's existing build command:

```bash
pnpm rspack build
```

After a successful build the process remains alive and prints two local URLs:

```text
Rspack Coverage is ready

Export usage: enabled
Source locations: exact

Reusable data:
/project/node_modules/.cache/rspack-coverage

Reopen without building:
rspack-coverage serve

Application:
http://127.0.0.1:4868/

Coverage report:
http://127.0.0.1:4868/__rspack_coverage__/

Press Ctrl+C to stop.
```

The successful compilation is saved locally before the ready message is printed. On later sessions, start the same report without invoking Rspack:

```bash
pnpm exec rspack-coverage serve
```

Run that command from the compiler context. It loads the latest saved snapshot, restores the last imported Coverage report when one exists, starts the application preview and analysis API, and opens the report. If the data directory is empty, it still opens an upload-ready workbench so a portable snapshot can be selected without first running Rspack. Useful standalone options are:

```bash
pnpm exec rspack-coverage serve --no-open --port 5000
pnpm exec rspack-coverage serve --data-dir /absolute/path/to/coverage-data
```

The saved snapshot contains only the compilation evidence this tool consumes: the build manifest, generated JavaScript and HTML, private source maps, a SQLite payload store for original sources, dependency/export indexes and module code generation, plus the latest Coverage recording and derived report. Non-JavaScript preview assets continue to come from the original Rspack output directory, so keep that directory when the recorded journey needs CSS, images, fonts, Wasm, or other emitted files. The two most recent distinct snapshots are retained so a watch-mode server can switch builds safely without unbounded cache growth.

Use **Download snapshot** in the report header to stream the current build, Coverage recording, and completed report into one `.rspack-coverage` file. On another running report, use the upper-right **Upload snapshot** button or drop that file anywhere on the page. The imported build becomes active only after the complete file has been written and verified, so an interrupted or invalid upload leaves the current report unchanged.

### Memory and disk model

Large payloads are disk-first. During the first compilation, private maps are spooled to temporary files and original sources plus reference edges are inserted into a temporary SQLite database instead of accumulating in JavaScript arrays. Final persistence copies one source/reference/code-generation record at a time, then releases lazily generated module code before moving to the next module. On restart, source text, code generation, export metadata and reference pages are queried from the saved database; the server does not reconstruct the complete reference or export graph in memory.

The v2 snapshot uses a 32 MiB SQLite page cache per open connection with memory mapping disabled. The Node server keeps the build manifest, source paths and report summaries in memory, so memory still scales with metadata count; payload memory is limited to the current asset/map/source/module request rather than total captured bytes. A Coverage analysis worker adds its own page cache while it is active and reads source contents one file at a time.

Portable `.rspack-coverage` files are uncompressed, length-delimited containers around the same disk-first v2 layout. Download and upload both stream one payload at a time and verify a SHA-256 trailer for every file; the browser sends the selected `File` directly and never calls `arrayBuffer()` on it. Only bounded path/checksum buffers and the existing snapshot metadata are materialized during import. The total portable-file guard is 32 GiB, while the existing 256 MiB limit still applies to any one asset, map, source, code-generation record, or metadata record.

To fail predictably instead of asking V8 to materialize a pathological blob, one stored asset, map, source, code-generation record or graph record is limited to 256 MiB. Chrome Coverage JSON is currently parsed in one worker and is therefore limited to 128 MiB. These are memory-safety guards, not total snapshot size limits. The snapshot database itself may be multiple gigabytes, and retaining two distinct snapshots can require roughly twice the disk space.

The paged module-reference API remains complete regardless of total edge count. Per-source Export analysis still prepares one worker message, so it rejects a source with more than 25,000 direct references instead of silently truncating evidence or risking an out-of-memory crash; use the paged reference view for that exceptional case.

## Record a user journey

1. Open **Application** from the report. Always record against this preview so generated script text matches the captured compilation.
2. Open Chrome DevTools → **More tools** → **Coverage**.
3. Choose JavaScript **Per block**, start recording and reload the page.
4. Exercise the page or user journey you want to understand.
5. Stop and export `Coverage-*.json`.
6. Drop the JSON file onto the analysis page.

Chrome's export contains each script URL, the generated script text and executed ranges. The importer matches URL path, UTF-8 content size, and SHA-256 content hash before accepting a script. A stale or different build is rejected instead of producing a plausible but incorrect report.

The browser streams the unparsed recording to the local `127.0.0.1` server. Coverage matching, source-map traversal, byte accounting, aggregation, and report generation run in a Node worker thread. Build assets and source maps are read incrementally from local files, and original sources are loaded immediately before their detail record is written rather than collected into one object. The main report contains only per-file summaries; source text and mapped-line state are stored in a Node sidecar, and full line objects are materialized only when a source drawer is opened. Large builds therefore do not require one giant JSON string containing every source file.

## How to read the report

- **Loaded**: final generated JavaScript bytes belonging to assets present in the imported recording.
- **Executed module code** (`moduleMetrics.executedBytes`): UTF-8 bytes from retained original-source lines covered by Chrome's executed ranges.
- **Unused module code** (`moduleMetrics.unusedBytes`): retained original-source bytes in a loaded Rspack module that did not execute in this recording. Each source line is counted once, so a large generated/minified mapping cannot inflate the current module. A line with any executed range is counted as fully executed; a retained loaded line with no executed range is unused. Source lines removed by tree shaking or minification, not-loaded chunks, and Rspack runtime/unmapped bytes are excluded. Lazy callback bodies, including an uncalled `load: () => import(...)`, remain unused for the recorded journey. This is an investigation signal, not guaranteed removable output size.
- **Module instances**: module rows are keyed by Rspack module ID, not only source-map path. If multiple loaded module instances share one original source, their per-asset execution evidence remains separate in both the metrics and source colors.
- **Asset unexecuted** (`metrics.unusedBytes`): all loaded-but-unexecuted final-asset bytes, including Rspack runtime and unmapped code. This remains available in the report API and chunk view, but is not shown as module `Unused`.
- **Module code not loaded** (`moduleMetrics.notLoadedBytes`): retained original-source bytes in modules whose chunks are absent from this recording. They are kept visually neutral because another route may need them.
- **Mapped**: generated bytes attributable to an original source through a final column-level source map.
- **Runtime / unmapped**: generated bytes for which the source map contains no original source mapping.

The Node worker streams every generated asset and source map one at a time, including assets absent from the recording, so removed, retained, loaded, and not-loaded module code use the same final-build evidence without collecting one giant in-memory payload.

The module investigation drawer has two independent statuses:

- Build: `retained`, `not-emitted`, or `unknown`.
- Runtime: `not-loaded`, `not-executed`, or `executed`.

`not-emitted` only describes the final map: a non-empty original line has no generated mapping. The report does not guess whether tree shaking, code generation, or minification removed it.

The drawer also provides:

- Lazy source loading from the Node sidecar, so opening one file does not deserialize every source.
- Exact `used` exports receive a purple underline. Selecting an export jumps directly to its captured module dependency graph; no hover card is created.
- Direct consumers, dependencies, referenced export names, and the shortest compilation path back to an entry.
- Selecting a graph node or edge loads the consumer snippet and highlights the captured dependency location.

The reference graph is a compilation dependency/export-usage graph, not a runtime call stack. Red means only that the imported recording did not execute a loaded range; it is never a deletion verdict.

Opening an original JS/TS module starts a separate, non-blocking **Export analysis** task. Tree-shaken (`unused`), unknown, type-only, namespace, and other conservative results remain ordinary source text without decoration. Reference chains are intentionally limited to captured compilation references; complex export-to-export propagation is not guessed.

## Options

```ts
new RspackCoveragePlugin({
  port: 4868,
  open: true,
  historyApiFallback: true,
  dataDir: "node_modules/.cache/rspack-coverage",
});
```

- The server always binds to `127.0.0.1`; host configuration is intentionally unavailable.
- When a port is occupied, the next port is tried, up to 100 ports.
- `CI=true` disables the plugin entirely so CI builds do not remain alive.
- Watch mode reuses the same server and replaces the compilation snapshot after each completed build.
- `dataDir` is resolved from the compiler context. It defaults to `node_modules/.cache/rspack-coverage`; set it to `false` to use process-local temporary data and disable no-build reopening.
- An absolute CDN `publicPath` is diagnosed and the local app preview is disabled. Use `auto`, a relative path, or a local path for the analysis build.

## Analysis build configuration

Accurate byte and export analysis requires full column source maps, tree shaking, and minification. When the effective Rspack configuration does not provide them, the plugin prints every adjustment to the console and enables:

- private full column source maps for JavaScript assets when the configured `devtool` is unsuitable
- `optimization.usedExports`, `sideEffects`, `providedExports`, and `innerGraph`
- `optimization.minimize` and, if the minimizer list is empty, Rspack's default minimizers

An existing full source-map mode or enabled optimization is preserved. `mode`, entry, chunking, and unrelated Rspack settings are not changed. When the plugin creates maps, it captures them privately and removes the temporary map assets from application output. The plugin also retains original module source (and upstream `sourcesContent` when available) so completely removed sources can still be inspected; application modules are not instrumented.

## Export usage data

Export status combines the current compilation's Stats and `moduleGraph`:

- Stats/moduleGraph `usedExports` and `providedExports` determine exact used/unused states when usage analysis is enabled by the user's build.
- Active dependency edges and `Dependency.ids` identify direct references and property paths.
- Logical dependency edges are streamed into a temporary disk ledger after module optimization but
  before `ConcatenatedModule` rewrites the graph, so concatenated children retain their own importer
  and dependency topology without holding the full graph in JavaScript memory.
- Module source maps translate loader-processed dependency locations back to original JS/TS when available.
- Babel parses original JS, JSX, TS, and TSX to locate named, aliased, declaration, default, re-export, export-star, and type-only export symbols.

The plugin enables `optimization.usedExports` before compilation so used and tree-shaken exports can be classified from the final ModuleGraph. The analysis runs on demand in a worker thread and is cached per build and source.

## Privacy and security

- The HTTP server listens only on `127.0.0.1`.
- Build-data API calls require a random per-process token embedded into the same-origin analysis page.
- CORS is not enabled.
- Successful build snapshots, the latest imported Coverage recording and its indexed report are kept in `dataDir` so they can be reopened without compiling. The cache retains the latest two distinct snapshots. Delete that directory to remove all retained data, or set `dataDir: false` for process-local temporary storage that is deleted when the build changes or server closes.
- Portable snapshot upload/download uses only the same authenticated `127.0.0.1` server. No snapshot bytes are sent to an external service.
- The browser keeps only the current summary report and source details that the user opens. Source details, module references, and consumer snippets are loaded on demand; re-analysis of the latest recording is served by the local Node process rather than IndexedDB.
- No telemetry, network upload, or external service is used.

As with any local build tool, the report can display source paths and `sourcesContent`. Do not expose the local port through a tunnel or proxy.

## First-version boundaries

- JavaScript only; CSS and Wasm Coverage entries are ignored.
- Loaded state comes from Coverage asset presence, not a Network timeline.
- No request timing, cache status, transfer size, waterfall, gzip, or Brotli module estimate.
- Per-function recordings can be imported but are explicitly marked lower precision.
- Source-to-generated attribution follows source-map mapping boundaries. Poor or missing maps lower mapping coverage rather than inventing precision.
- Export reference details retain pre-concatenation ModuleGraph evidence and derive a bounded, on-demand
  importer-export chain from active dependency edges plus each importer's used exports. A single
  carrying export is shown as exact; multi-export branches remain explicitly conservative.
- The Opportunities view ranks factual signals. It never labels unexecuted bytes as guaranteed savings.
