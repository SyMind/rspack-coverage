# star-export-loader

`star-export-loader` is a pre-loader for Rspack. It recognizes namespace runtimes generated by
Rollup, Rolldown, and esbuild, then restores them as native ESM namespace re-exports. This gives
Rspack per-export usage information again.

Use it for ESM libraries that have already been bundled upstream. You may not control the library
source, but you still need to include it in another Rspack build and want `namespace.foo` to retain
only the code that `foo` needs.

## Why it exists

A library may start with:

```js
export * as utils from "./utils.js";
```

When Rollup, Rolldown, or esbuild publishes that library, it may turn the namespace into a runtime
object:

```js
const foo = fooFactory();
const bar = barFactory();

// Rollup
const rollupUtils = Object.freeze({ __proto__: null, foo, bar });

// Rolldown
const rolldownUtils = __exportAll({
  foo: () => foo,
  bar: () => bar,
});

// esbuild
const esbuildUtils = {};
__export(esbuildUtils, {
  foo: () => foo,
  bar: () => bar,
});

export { esbuildUtils, rolldownUtils, rollupUtils };
```

The next bundler sees object initialization and getter maps. The local bindings referenced while
constructing those objects usually enter the usage graph, so `bar` may remain in the final bundle
even when the consumer only reads `utils.foo`.

The loader removes that runtime wrapper and gives Rspack a set of static ESM edges. Rspack can then
propagate export usage through `namespace.foo` and remove unused code according to its normal
side-effect rules.

## Installation

This package currently exists only in this monorepo and has not been published to npm. A package in
the workspace can install it with:

```bash
pnpm --filter your-app add -D star-export-loader@workspace:*
```

It requires Node.js 22.12.0 or later. The consuming project must provide `@rspack/core` 1.0.0 or
later.

## Rspack setup

Limit the rule to a reviewed distribution entry and run the loader before other source transforms:

```js
// rspack.config.mjs
import { createRequire } from "node:module";

const require = createRequire(import.meta.url);

export default {
  module: {
    rules: [
      {
        test: /node_modules[\\/]affected-library[\\/]dist[\\/]index\.js$/,
        enforce: "pre",
        use: [
          {
            loader: require.resolve("star-export-loader"),
          },
        ],
      },
    ],
  },
};
```

Avoid applying the rule to all of `node_modules`. Upstream bundlers may change their generated
code between releases. Matching an exact package entry keeps the semantic change reviewable and
limited to code that you have validated.

## Generated module structure

Suppose one entry contains all three runtime forms and also exports `untouched`:

```js
const foo = fooFactory();
const bar = barFactory();

const libRollup = Object.freeze({
  __proto__: null,
  fooRollup: foo,
  barRollup: bar,
});

const libRolldown = __exportAll({
  fooRolldown: () => foo,
  barRolldown: () => bar,
});

const libEsbuild = {};
__export(libEsbuild, {
  fooEsbuild: () => foo,
  barEsbuild: () => bar,
});

const untouched = 42;
export { libEsbuild, libRolldown, libRollup, untouched };
```

The loader creates one shared virtual implementation module. It keeps the original implementation,
removes each accepted runtime and its namespace export specifier, then exports the bindings needed
by the facades:

```js
// virtual entry
const foo = fooFactory();
const bar = barFactory();
const untouched = 42;
export { untouched };

export {
  foo as fooEsbuild,
  bar as barEsbuild,
  foo as fooRolldown,
  bar as barRolldown,
  foo as fooRollup,
  bar as barRollup,
};
```

Each accepted namespace gets its own facade:

```js
// facade for libEsbuild
export { fooEsbuild, barEsbuild } from "virtual:entry";

// facade for libRolldown
export { fooRolldown, barRolldown } from "virtual:entry";

// facade for libRollup
export { fooRollup, barRollup } from "virtual:entry";
```

The public entry only re-exports those modules:

```js
export * as libEsbuild from "virtual:facade-esbuild";
export * as libRolldown from "virtual:facade-rolldown";
export * as libRollup from "virtual:facade-rollup";
export { untouched } from "virtual:entry";
```

The `virtual:*` specifiers above illustrate the module relationships. The loader uses the original
resource path with an internal query and explicitly replays the active loader chain. Virtual
modules therefore continue to work when the rule has a `resourceQuery` condition.

All facades share one virtual implementation module, so the original entry evaluates once. If two
namespaces expose the same export name from different bindings, the loader creates an internal
alias in the virtual implementation to keep them isolated.

## Built-in adapters

| Adapter | Recognized output |
| --- | --- |
| `rollup` | An object literal wrapped in `Object.freeze(...)` with `__proto__: null`; supports direct properties, simple getters, and the optional `Symbol.toStringTag` wrapper |
| `rolldown` | An object literal wrapped in `__exportAll(...)`; supports direct properties and getter maps that return one identifier |
| `esbuild` | An empty namespace object followed by `__export(target, getterMap)`; it can also identify minified helper names from the helper's `for...in` and `Object.defineProperty` structure |

All three adapters are enabled by default. Matching is primarily structural, while helper names
locate candidate calls. The esbuild adapter can also infer minified names from the helper
implementation.

## Options

```js
{
  loader: require.resolve("star-export-loader"),
  options: {
    adapters: ["rollup", "esbuild", "rolldown"],
    esbuildHelperNames: ["__export"],
    rolldownHelperNames: ["__exportAll"],
  },
}
```

| Option | Type | Effective default | Purpose |
| --- | --- | --- | --- |
| `adapters` | `Array<"rollup" \| "esbuild" \| "rolldown">` | All built-in adapters | Run only the selected matchers |
| `esbuildHelperNames` | `string[]` | `["__export"]` | Add trusted esbuild helper names used by the project |
| `rolldownHelperNames` | `string[]` | `["__exportAll"]` | Add trusted Rolldown helper names used by the project |

Additional helper names extend rather than replace the defaults. Loader options accept only the
built-in adapters. The programmatic API also accepts custom `NamespaceRuntimeAdapter`
implementations.

## Conservative bailouts

The loader rewrites only candidates that it can prove statically. It skips a namespace when any of
the following conditions apply:

- The namespace is not a unique top-level binding or is reassigned later.
- A local ESM export specifier does not publish the namespace.
- Code reads the namespace outside its runtime initializer and export declaration.
- A member name cannot be emitted safely as a static export name.
- A member value does not resolve directly to one identifier, or the object contains a spread,
  duplicate keys, or another dynamic structure.
- More than one adapter matches the same namespace.
- The module contains an unbounded `export * from "..."`; this bails out the entire module.
- A local binding shadows `Object` or `Symbol` in a matching Rollup form.

For example, an internal spread prevents a facade from replacing the original object:

```js
const commands = __exportAll({ clearContent: () => clearContent });

function addCommands() {
  return { ...commands };
}

export { commands };
```

The loader keeps this runtime. Other independent namespaces in the same file may still be
transformed.

## Tree-shaking and semantic boundaries

The loader restores export usage information; it does not declare member initializers
side-effect-free. Rspack's normal side-effect analysis still decides whether it can remove
`fooFactory()`.

The result also depends on how consumers read the namespace. `Object.keys(namespace)`, object
spread, and other forms of dynamic enumeration require Rspack to retain the entire namespace and
usually provide no size reduction.

The transformed value follows the ESM namespace semantics generated by the final bundler. If an
application depends on the upstream runtime object's `Object.isFrozen()` result, prototype,
extensibility, or exact property descriptors, run targeted semantic checks before enabling the
loader for that entry.

## Inspecting the transform

`star-export-loader/api` exposes the analysis and rendering functions, so you can inspect a plan
before adding it to a build:

```js
import { readFile } from "node:fs/promises";
import {
  createStarExportPlan,
  renderStarExportEntry,
  renderStarExportFacade,
} from "star-export-loader/api";

const filename = "node_modules/affected-library/dist/index.js";
const source = await readFile(filename, "utf8");
const plan = createStarExportPlan(source, { filename });

console.log(plan.diagnostics);
console.log(plan.virtualEntrySource);

const facadeRequests = plan.facades.map((facade) => `virtual:facade-${facade.id}`);
console.log(renderStarExportEntry(plan, "virtual:entry", facadeRequests));

for (const facade of plan.facades) {
  console.log(renderStarExportFacade(facade, "virtual:entry"));
}
```

The main fields returned by `createStarExportPlan` are:

- `transformed`: whether the plan accepted at least one namespace.
- `virtualEntrySource` and `virtualEntryMap`: the shared implementation module and its source
  map.
- `facades`: the adapter, public namespace names, member mappings, and internal aliases.
- `remainingExports`: real exports still forwarded from the virtual implementation.
- `diagnostics`: rejection reasons such as parse errors, ambiguity, internal references, and
  reassignment.

## Results with `@tiptap/core`

This repository includes results from a production A-B-A test using the ESM distribution entry of
`@tiptap/core@3.31.1` and Rspack 2.2.1. The test targeted Node and emitted one CommonJS asset.
`@tiptap/pm` remained external in both the baseline and optimized builds. These numbers describe
that controlled entry only, not the total savings of a browser application.

The entry contained three Rolldown `__exportAll` namespaces:

- `commands` had 62 members. `Commands.addCommands()` also spreads it internally, so the loader
  bailed out.
- `extensions` had 11 members and was converted into a dedicated facade.
- `markdown` had 7 members and was converted into a dedicated facade.

The shared virtual implementation reduced the number of `__exportAll` calls from three to one.
The remaining call belongs to `commands`, which still has an internal reader. The readable form
of the transformed public entry is:

```js
export * as extensions from "virtual:facade-extensions";
export * as markdown from "virtual:facade-markdown";
export { commands /* and the remaining direct exports */ } from "virtual:entry";
```

Static access to one namespace member produced the following results. Baseline A and baseline B
were byte-identical in every scenario, and the optimized runtime result matched both baselines.

| Scenario | Raw size | Gzip size | Result |
| --- | ---: | ---: | --- |
| `markdown.parseAttributes` | 70,160 → 64,367 B | 22,439 → 20,388 B | Raw decreased by 5,793 B (8.26%); gzip decreased by 2,051 B (9.14%) |
| `extensions.ClipboardTextSerializer` | 63,121 → 62,855 B | 19,932 → 19,899 B | Raw decreased by 266 B (0.42%); gzip decreased by 33 B (0.17%) |
| `commands.clearContent` | 62,855 → 62,855 B | 19,895 → 19,895 B | The conservative bailout left the output unchanged |
| Direct-export control | 62,851 → 62,851 B | 19,891 → 19,891 B | No namespace runtime was involved; the output was unchanged |

`Object.keys(markdown)` required all seven members to remain and increased the optimized output by
3 raw bytes and 23 gzip bytes. In this Rspack output, probes for namespace keys,
`Symbol.toStringTag`, prototype, extensibility, frozen state, and property descriptors matched
the baseline. That result does not replace semantic validation for other packages or output
formats.

## Development and validation

Run these commands from the monorepo root:

```bash
pnpm --filter star-export-loader typecheck
pnpm --filter star-export-loader test
pnpm --filter star-export-loader build
```

Run the complete repository checks with:

```bash
pnpm verify
```

The unit tests cover adapter matching, alias conflicts, and conservative bailouts. The Rspack
integration test compares bundles with and without the loader. It verifies that unused members
disappear, runtime behavior stays unchanged, the shared implementation evaluates once, and both
raw and gzip sizes decrease.
